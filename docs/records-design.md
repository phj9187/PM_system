# 기록파트 설계: 원본 기록과 Notion 정리본

상태: 설계 초안 (2026-11-23). 코드는 아직 없다.

## 1. 확정된 원칙

- **원본 기록은 PM_system이 관리한다.** 대시보드 변경 이력, Discord 메시지 출처, AI 정리 결과, 확정 결정, 확인 필요 항목은 앱의 저장소에 남긴다. 근거 추적과 정확성의 기준은 언제나 이 원본이다.
- **Notion은 사람이 읽는 정리본이다.** 원본에서 만들어 발행하고, 보기 쉽게 다듬는 것에 집중한다.
- **발행은 단방향이다.** Notion에서 고친 내용은 원본으로 돌아오지 않는다. 정리본은 언제든 원본에서 다시 만들 수 있어야 한다.

## 2. 데이터 흐름

```
대시보드 저장 ─┐
               ├─▶ 원본 기록 저장소 ─▶ 분류·검증 ─▶ (필요 시) Gemini 정리 ─▶ 원본에 결과 저장
Discord 수집 ──┘                                                            │
                                                                            ▼
                                                    발행기 ─▶ Notion 정리본 (단방향)
```

수집·정리 주기와 Notion 발행 주기는 따로 둔다. 원본은 자주 쌓이고, 정리본은 정해진 주기에 묶어서 발행한다.

## 3. 원본 기록 저장소 구성

모든 레코드는 고유 `id`, `project_id`, `created_at`을 가진다. 원본 레코드는 덮어쓰지 않고 추가만 한다(append-only). 정정은 새 레코드로 남기고 이전 레코드를 가리킨다.

| 저장소 | 내용 | 비고 |
| - | - | - |
| `change_events` | 대시보드 저장 시 이전 상태와 비교한 변경분(항목 종류, 항목 ID, 필드, 이전 값, 새 값, 변경자, revision) | 현재 version 1 상태에는 이력이 없으므로 저장 시점 비교로 만든다 |
| `source_messages` | Discord 메시지 참조(서버·채널·메시지 ID, 작성 시각, 수정 시각, 삭제 여부, 원문, 원문 링크) | 원문은 비공개 저장소에만 둔다. 수정되면 새 버전을 추가하고, 삭제되면 삭제 표시만 남긴다 |
| `digests` | AI 정리 결과(기간, 요약 본문, 사용한 근거 ID 목록, 모델, 생성 시각, 오류) | 근거 ID 없이 저장하지 않는다 |
| `record_items` | 정리본의 단위 항목(아래 4장의 분류, 본문, 근거 ID, 관련 대시보드 항목) | Notion에 나가는 것은 이 항목들이다 |
| `decisions` | 사람이 확정한 결정(내용, 확정자, 확정 시각, 근거, 관련 결정 요청 ID) | AI가 만들 수 없다 |
| `review_queue` | 확인 필요 항목(충돌 내용, 양쪽 근거, 처리 상태, 처리자) | 사람이 처리하면 결과를 원본에 남긴다 |
| `publications` | 발행 이력(대상 Notion 페이지·DB, 기간, 발행한 항목 ID와 해시, 결과, 오류) | 재발행·중복 방지·재시도의 기준 |

저장 위치: 초기에는 기존 서버처럼 `data/private/` 아래 파일(JSON Lines)로 시작하고, 상시 운영 환경이 정해지면 데이터베이스로 옮긴다. `data/private/`와 `*.sqlite`는 이미 Git에서 제외되어 있다.

## 4. 기록 항목의 분류

| 분류 | 의미 | 누가 만드나 |
| - | - | - |
| 제안 | 누군가 의견이나 대안을 낸 것 | 수집·AI 분류 |
| 추정 | AI가 대화에서 추론한 상태(예: "작업 A가 늦어지는 것으로 보임") | AI |
| 진행 보고 | 완료·착수·지연 등 실제 진행 사실(대시보드 변경 또는 명시적 보고) | 대시보드·수집 |
| 확정 결정 | 사람이 확정한 결정 | 사람만 |
| 확인 필요 | 근거끼리 충돌하거나 판단이 불확실한 것 | 검증 단계 |

규칙:
- AI의 요약·추천은 확정 결정이 될 수 없다. 확정 결정으로 바꾸는 것은 사람의 명시적 행동(대시보드의 결정 요청 완료 처리 등)뿐이다.
- 모든 항목은 근거(대시보드 변경 ID 또는 Discord 메시지 ID)를 하나 이상 가진다.
- Notion 정리본에서도 분류가 눈에 보이게 표시한다.

## 5. 충돌과 확인 필요

- 대시보드 상태와 대화 내용이 다르면 AI는 공식 상태를 바꾸지 않고 `review_queue`에 올린다. 예: 대시보드는 "진행 중"인데 대화에서는 "완료했다"고 함.
- 확인 필요 항목은 정리본에 별도 묶음으로 드러낸다. 사람이 처리하기 전까지 정리본에서 사실로 서술하지 않는다.
- 처리 결과(어느 쪽이 맞았는지, 대시보드를 고쳤는지)는 원본에 남기고 다음 발행에 반영한다.

## 6. 수정·삭제된 Discord 메시지

- 원본: 수정은 새 버전으로, 삭제는 삭제 표시로 보존한다. 근거 링크가 끊겨도 원본에서는 추적할 수 있다.
- 정리본: 다음 발행 때 해당 메시지를 근거로 한 항목을 다시 만든다. 이미 발행된 지난 기간 기록을 고칠지, "정정" 메모만 덧붙일지는 미정이다(8장).
- 삭제된 메시지의 원문은 정리본에 다시 싣지 않는다.

## 7. Notion 발행 규칙

- 발행기는 `record_items`, `decisions`, `review_queue`만 읽어 정리본을 만든다. 원본 원문을 그대로 붙이지 않고 요약과 원문 링크를 쓴다.
- 같은 항목을 여러 번 발행해도 중복되지 않도록 원본 ID와 Notion 블록·행 ID의 대응을 `publications`에 저장한다.
- 자동 관리되는 페이지·DB 상단에 "PM_system이 자동으로 만드는 기록입니다. 여기서 고친 내용은 다음 발행 때 덮어쓰일 수 있습니다."라는 안내를 둔다. 사람이 자유롭게 쓰는 메모 영역은 자동 관리 영역과 분리한다.
- 발행 실패는 `publications`에 기록하고 다음 주기에 재시도하며, 실패 사실을 대시보드에 표시한다.
- Notion 통합 토큰은 Gemini 키·Discord Bot 토큰과 같은 서버 비밀 저장소에 두고, 화면에는 연결 여부만 표시한다. 백업 JSON, 브라우저 저장소, 로그, 노트북 출력, GitHub에 넣지 않는다.

### Notion 형식 후보 (미정)

| 후보 | 구성 | 장점 | 단점 |
| - | - | - | - |
| A. 페이지 + DB 혼합 | 프로젝트별 "현재 현황" 페이지 1개, "기간별 기록" DB, "결정 로그" DB | 현황은 읽기 쉽고, 기록·결정은 필터·정렬 가능 | 구성 요소가 3개 |
| B. 페이지만 | 현재 현황 페이지 + 기간마다 하위 페이지 | 단순하고 읽기 편함 | 검색·필터가 약함 |
| C. DB만 | 항목 하나가 한 행인 단일 DB, 보기(view)로 현황·기간·결정 구분 | 중복 방지·갱신이 쉬움 | 사람이 훑어보기엔 덜 친숙 |

추천은 A다. "현재 현황"은 매번 통째로 다시 쓰고, 기간별 기록과 결정 로그는 행 단위로 추가·갱신한다.

## 8. 미정 사항

1. Notion 형식(7장 후보)과 대상 워크스페이스·상위 페이지
2. 발행 주기(매일, 매주, 마일스톤 등)와 수집·정리 주기
3. 수집할 Discord 채널과 프로젝트 매핑
4. 지난 기간 정리본을 고칠지, 정정 메모만 붙일지
5. 확정 결정으로 인정하는 사람의 행동(결정 요청 완료 처리만인지, 별도 승인 절차인지)
6. 원본 저장소의 상시 운영 환경과 보존 기간

## 9. 구현 순서 제안

1. 대시보드 저장 시 변경분을 `change_events`로 남기기 (Discord·Notion 없이 바로 가능)
2. `record_items` 분류 규칙과 기간별 정리본을 Markdown으로 만들어 미리보기
3. Notion 형식 확정 후 발행기 구현(멱등 발행, 안내 문구, 실패 기록)
4. Discord 수집이 준비되면 `source_messages`와 확인 필요 처리 연결
